# 中文技术写作

技术文档的任务是让读者准确理解、使用、维护或评审系统。正式不等于公文腔，自然也不等于工位口语。

## 先确定文档类型

不同文档保留的信息不同：

- **参考文档：** 当前接口、字段、行为、限制和错误；
- **使用指南：** 目标、前置条件、操作步骤、结果和排障；
- **架构或设计说明：** 问题、约束、职责、数据流、关键决策和边界；
- **ADR：** 决策、背景、备选方案、取舍和后果；
- **迁移指南：** 旧状态、新状态、迁移步骤、兼容性和回退；
- **复盘：** 事实时间线、影响、根因、处置和改进；
- **README：** 项目用途、快速开始、核心概念和继续查阅的位置；
- **代码注释：** 代码无法自明的原因、约束、风险和外部约定；
- **PR/提交说明：** 改了什么、为何需要、如何验证和剩余风险。

不要把 ADR 的方案比较、复盘的时间线或 PR 的修改过程带入普通参考文档。

## 围绕读者的问题组织

章节顺序应来自读者的理解路径，不来自模型阅读代码或原文档的顺序。常见问题包括：

- 这个组件解决什么问题；
- 何时会被调用；
- 输入、输出和状态怎样变化；
- 各角色或模块分别负责什么；
- 哪些条件和边界会改变行为；
- 如何验证结果；
- 失败后怎样定位和恢复。

不是每篇文档都要回答全部问题。只保留与文档目的相关的部分。

## 开头与收尾

开头直接交代必要的对象、场景或问题。不要先写：

- 本文将介绍什么；
- 这份文档不是什么；
- 随着某项技术不断发展；
- 为什么这篇文档“值得阅读”；
- 接下来分几部分展开。

标题和目录已经承担导航作用。正文从第一个有效信息开始。

结尾停在最后一个具体结论、操作或限制上。没有真实后续计划时，不补“未来展望”“持续优化”或泛化总结。

## 描述当前有效状态

普通文档和注释默认写当前系统如何工作：

- “请求先经过权限检查，再进入任务队列。”
- “缓存键由账号和区域共同组成。”

不要写成修改记录：

- “这次新增权限检查，替代了此前直接入队的方式。”

只有 changelog、迁移指南、ADR、复盘或用户明确要求比较版本时，才保留历史视角。旧讨论对当前行为没有解释价值时直接删除。

## 段落、列表和标题

- 段落承载因果、推理和解释；列表承载并列项、步骤、条件或可扫描的参考信息。
- 不把一个连续论证拆成“第一、第二、第三”来制造结构感。
- 小标题用于定位内容，不用于包装观点。使用“缓存策略”“失败处理”，不要使用“破局之道”“双轮驱动”。
- 标题后直接进入细节，不先复述标题或预告本节内容。
- 不要求每节长度相同。重要处展开，简单处一句说清。

## 句子

- 主语、动作和对象应当清楚。避免“达标则结束，卡住则上报人工”这类依赖团队默契的电报体。
- 使用准确动词，不用“进行、作出、开展、实现”承包所有动作。
- 限定词只保留必要的一层。不要叠加“可能、或许、一定程度上、通常情况下”。
- 连接词用于真实逻辑跳转，不按段落机械投放“因此、同时、此外、值得注意的是”。
- 允许自然的长短句变化，不人为把长句切成连续短句，也不为显得完整堆多层定语。
- 技术文档默认中立、平实。不要强行加入“我们认为”“不妨思考”“可以看到”等讲解者姿态。

## 术语与英文

先读取 `terminology.md`。

- 标准 API、类名、协议名、库名和业内通用缩写可以保留英文。
- 英文术语第一次出现时，只有在中文名称能帮助理解时才补中文；不要为每个词强造译名。
- 同一个概念保持同名。不要为了避免重复在“模块、组件、单元、能力”之间轮换。
- 代码标识符与面向读者的概念名可以不同，但需要明确对应关系。

## README 和指南

README 优先帮助读者开始使用，而不是展示作者对项目的完整理解：

1. 项目解决什么问题；
2. 最短可运行路径；
3. 必要前置条件和配置；
4. 核心概念；
5. 常见失败和继续查阅的位置。

安装步骤必须能执行，命令、路径和版本要求保持精确。不要用宣传卡片、无意义统计数字或大段价值描述挤占快速开始。

## 架构和设计说明

设计文档需要解释“为什么”时，写与决策直接相关的约束和后果，不复述所有讨论过程。

普通架构说明只保留当前架构和关键理由。若要记录备选方案，明确文档是 ADR 或决策记录，并说明：

- 方案解决了什么；
- 哪个约束导致选择；
- 接受了什么代价；
- 何种条件变化时需要重审。

不要把每个被否决想法都保存为“供未来参考”。没有未来判断价值的过程信息应删除。

## 代码注释

注释解释代码本身不容易看出的内容：

- 为什么必须这样做；
- 外部系统有哪些非显然约束；
- 哪个边界容易出错；
- 修改时必须维持什么不变量。

不要逐行翻译代码，不写调试对话，不记录已经失效的替代方案。临时 workaround 应说明触发条件和移除条件，而不是讲故事。

## PR 与提交说明

优先写：

- 当前改动；
- 必要原因；
- 用户或系统行为变化；
- 验证方式；
- 已知风险或后续项。

不要加入“为了让结构更优雅”“经过深入分析”等无证据评价。未采用的方案只有在评审者需要据此判断风险时才提及。

## 交付前

确认文档能让目标读者完成其任务，同时没有：

- 作者与读者之间的对话残留；
- 与文档目的无关的背景；
- 已废弃且无判断价值的过程；
- 英文语序和逐词翻译；
- 依赖团队黑话才能补全的动作；
- 为结构完整而添加的空章节、总结和展望。

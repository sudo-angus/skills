# UI 文案

UI 文案帮助用户识别状态、作出选择、完成操作和从错误中恢复。界面不是产品文档的缩略版，也不是实现过程的展示区。

## 信息顺序

用户通常按以下顺序读取：

1. 这里是什么；
2. 当前状态怎样；
3. 我需要做什么；
4. 做完会发生什么；
5. 出错怎么办。

按这个顺序组织信息。实现原理、设计原因和完整规则放到次级帮助中。

## 组件职责

### 标题

说明任务、对象或状态。标题不负责宣传价值，也不重复整段正文。

优先使用名词短语或明确动作，如“自动回流设置”“删除账号”“重新连接”。避免“一键开启高效协作”“关于自动回流你需要知道的事”。

### 字段标签

说明用户要提供或选择什么。保持稳定、可扫描，不把条件和解释塞进标签。

### 辅助说明

只补充一个不明显的输入要求、行为结果或限制。若需要解释多个规则，移到帮助页面、提示浮层或折叠区。

辅助说明应从用户动作出发，不从实现机制出发。能写“请先将机器人加入该群”时，不写“否则通知链路无法解析群成员”。

### 开关和选项

选项名称描述功能或状态，说明文字描述开启后的效果。不要把“开启/关闭”同时写进名称和控件值。

不同选项有风险差异时，直接说明差异和后果；不要写成设计方案比较。

### 按钮

按钮名称说明点击后的结果：保存、删除、重试、重新连接、导出、继续。避免“确定”“好的”“处理”等无法预判结果的泛化动词；标准平台弹窗中语义已明确时可以沿用系统惯例。

危险操作使用具体动作名称，不用带情绪的警告词替代动作。

### 状态与成功提示

确认发生了什么，以及是否还需要下一步。没有后续动作时，一句确认即可，不加庆祝、评价或“感谢耐心等待”。

### 错误信息

至少回答两个问题：

- 发生了什么；
- 用户现在能做什么。

必要时再说明原因。不要展示调用栈、内部错误码、解析流程或责任归属，除非目标用户需要这些信息排障，并且产品明确把它们作为公开诊断信息。

错误无法由用户修复时，说明系统会怎样处理，或提供明确的求助入口。不要只写“操作失败，请稍后重试”，也不要承诺并不存在的自动恢复。

### 警告与确认

说明具体风险、影响范围和是否可恢复。只有操作确实需要二次确认时才使用确认弹窗。

不要用长篇解释逼用户阅读后再点击。复杂影响应在进入危险操作前逐步告知。

## 弹窗和设置页

弹窗中的内容应围绕一个决定或一个任务。常见顺序是：

- 一句说明设置的效果；
- 必要字段和选项；
- 与当前选择直接相关的限制；
- 明确的取消与提交动作。

以下内容通常不应占据弹窗主体：

- 后台怎样创建任务、修改评审人或调用机器人；
- 系统内部使用哪个账号执行；
- 为什么产品团队选择这套方案；
- 哪种内部配置“最稳”；
- 不影响用户操作的角色分工和实现异常；
- 把多个内部对象用斜杠拼成的“摘要”。

若这些信息能帮助少数高级用户排障，提供“查看规则”或“了解详情”，不要全部平铺。

## 技术产品中的 UI

面向研发、运维或 QA 的界面可以使用 MR、branch、build、SDK 等目标用户熟悉的术语，但仍应满足：

- 术语在产品或团队中已有稳定含义；
- 信息会改变用户配置、判断或排障动作；
- 文案说清行为，不依赖作者与读者的私下默契；
- 口头黑话不直接变成正式标签。

“目标用户懂技术”不是展示内部过程的理由。

## 语言

- 一句话只承担一个主要作用。
- 优先使用“保存后生效”“检查未通过”“请重新连接”等直接说法。
- 少用“您可以通过……来实现……”“系统将会对……进行……”一类绕行句式。
- 不写“需要注意的是”“这里并不是”“一句话理解”“简单来说”等聊天或讲义残留。
- 不为了显得友好加入无用寒暄、感叹号、emoji 和拟人化评价。
- 不为了显得简洁而省掉动作主体、条件或结果。

## 最终检查

逐项确认：

- 用户能否在几秒内找到需要操作的字段和按钮；
- 每条说明是否会改变用户行为或防止误解；
- 是否出现只有实现者才能理解的词；
- 错误是否给出恢复方向；
- 重要风险是否在操作前出现；
- 详细规则是否占据了不合适的位置；
- 删除所有辅助说明后，字段和按钮是否仍有基本可理解性。

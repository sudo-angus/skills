# 中文内容写作

目标是让最终内容像熟悉产品和上下文的人写给目标读者：信息取舍合理，中文自然，术语稳定，不残留聊天过程、推理过程或英文句法。

## 不可让步的要求

1. **事实与行为准确。** 不编造事实、数字、限制、实现方式、用户能力或第一人称经历。
2. **只写最终载体需要的内容。** 上下文中出现过的信息不因此自动进入成品。
3. **内部过程不外露。** 提示词约束、设计取舍、被否决方案、调试记录和写作说明默认留在内部。
4. **沿用项目术语。** 先查现有 UI、文档、本地化资源和代码库，再决定名称；不自行创造中文技术词、简称或单字黑话。
5. **只交付终稿。** 审校过程在内部完成。除非用户明确要求诊断或备选方案，不输出初稿、审稿清单、写作理由或“我做了哪些调整”。

## 第一步：判断任务

动笔前确定四件事：

- 最终载体是什么；
- 读者是谁，此刻要完成什么；
- 输入是完成稿、工作素材，还是两者混合；
- 哪些事实、条件、占位符和既有术语必须原样保留。

能从仓库、界面和相邻文案中判断时，先自行检查。只有缺失信息会改变行为、风险或对外含义时才提问。

### 完成稿

用户要求润色、改写、压缩或去 AI 味时，保留实质事实、要求、承诺、数字和边界。可以删除重复、空话、对话残留和无作用的元说明，但不得把必要条件当作冗余删掉。

### 工作素材

需求讨论、代码、日志、提示词、设计约束、探索笔记和多份文档只是素材。根据最终载体重新选择和组织信息，不承担“把素材中的每个论断都写出来”的义务。

### 混合输入

先识别必须保留的成稿部分，再把其余上下文当作素材。不要因为某段文字写得完整，就默认它适合原样进入最终载体。

## 第二步：按载体读取规则

只读取当前任务需要的参考文件，不要无条件加载全部 references。

| 载体 | 必读参考 |
| --- | --- |
| 弹窗、设置项、按钮、提示、错误、通知、空状态等 UI 文案 | `references/content-boundary.md`、`references/ui-copy.md`；涉及技术概念时再读 `references/terminology.md` |
| README、技术方案、接口说明、使用指南、代码注释、PR/提交说明 | `references/content-boundary.md`、`references/technical-writing.md`、`references/terminology.md` |
| 用来讲解系统或框架的 HTML、网页、可视化说明 | `references/content-boundary.md`、`references/explainer-page.md`、`references/terminology.md` |
| 已有中文长文的润色、改写或去 AI 味 | `references/natural-chinese.md`；技术内容同时读 `references/terminology.md` |

以下情况还要读取 `references/natural-chinese.md`：输出包含多个完整段落、用户明确要求自然中文或去 AI 味，或者初稿已经出现模板化结构、翻译腔和生造词。

## 第三步：筛选信息

先决定“写什么”，再决定“怎么写”。

优先保留：

- 读者当前需要知道的状态；
- 读者必须执行的动作；
- 操作会产生的结果、风险和不可逆影响；
- 输入要求、适用条件、失败原因和恢复办法；
- 理解系统所必需的背景、边界和例外。

默认不进入最终内容：

- 模型如何理解任务、如何组织答案；
- 作者为何采用这种排版或措辞；
- 用户提示中的“不要……”“避免……”等约束本身；
- 已废弃方案、试错经过和无后续价值的历史讨论；
- 只有实现者需要知道的内部机制、临时名、调试结论和协作细节；
- 为显得完整而补出的背景、意义、总结和展望。

约束用于改变成品，不是成品的内容来源。例如，用户要求“不要暴露内部账号”，结果应是删掉该账号，而不是写一句“这里不会暴露内部账号”。

描述现状时直接写当前有效结论。只有变更日志、迁移指南、ADR、复盘和审计记录等天然需要历史视角的文档，才保留“原来怎样、后来为何改变”。

## 第四步：写作

- 语域服从载体。UI 简洁、可执行；技术文档正式但自然；内部聊天可以口语化，但不能把聊天腔复制到文档和界面。
- 使用具体主语和动作。能写“系统检查配置”时，不写“对配置进行检查”；能写“保存后生效”时，不写“保存操作完成后将会被应用”。
- 需要解释时补足因果和边界，不用省略主体的电报体，也不靠标题、加粗、卡片或列表代替论述。
- 列表只承载真正并列、需要扫描或需要逐项执行的内容。连续推理写成段落。
- 读者本来不会想到 A 时，直接陈述 B，不先制造“不是 A，而是 B”的假对照。
- 不创造简称、组合词、单字动词和逐词对应的中文译法。没有稳定中文说法时，保留约定俗成的英文术语通常比生造中文更清楚。
- 中文标点、空格和术语写法与项目现有内容保持一致。

## 第五步：内部终审

提交前按顺序检查：

1. **内容边界：** 是否把提示词、讨论过程、设计理由或实现细节写给了不需要知道的读者？
2. **任务完成：** 读者能否判断当前状态、下一步动作、结果和失败后的处理方式？
3. **事实保真：** 是否丢失了必要条件、占位符、数字、警告或行为结果？是否新增了无依据的信息？
4. **术语：** 新出现的中文技术词或缩写是否在项目中已有依据？英文词是否被机械直译？
5. **中文：** 是否有对话残留、讲义腔、翻译腔、空泛对照、机械排比、均匀段落或过度格式化？
6. **载体：** 这段内容放在当前组件或文档类型中是否合适？应该移到帮助文档的内容是否仍挤在主界面？

发现问题后直接修改终稿，不在交付物中解释审校过程。

## 修改文件时

- 保留代码块、frontmatter、链接目标、变量、占位符、格式化 token、转义符和机器读取结构。
- 本地化字符串中的 `%@`、`%d`、`{name}`、ICU 语法和换行控制不得擅自改变。
- 修改范围以完成当前任务为限，不顺手统一整份文档或整个产品的文风。
- 现有文案与本 skill 冲突时，先判断它是项目约定还是历史问题。项目明确约定优先；明显错误可以在当前范围内修正。
